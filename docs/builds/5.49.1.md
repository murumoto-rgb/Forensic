* **Summary:** Binary backfill from R2 so iOS works fully without iCloud Drive — simulator, fresh install on a real device, restored-from-backup device, anyone who picks up the app on a new phone. Previously iOS uploaded photos + plans to R2 (PhotoSyncer) but never downloaded them back; a device that pulled the manifest from the server would see "missing file" placeholders for every photo / plan whose binary lived only in R2. Cohort hit hardest was the iOS Simulator, which intentionally skips iCloud Drive to dodge the simulator iCloud-daemon hangs — every project pulled from the server was effectively a metadata-only shell. New `BinaryBackfillService` (`@Observable @MainActor`) walks `store.activeProjects`, for every photo + plan whose local file is missing fetches the bytes via the existing presigned-URL endpoints (`/v1/projects/:id/photos/:id/image`, `/v1/projects/:id/plans/:id/image`), and writes to the same local path the manifest expects. Bounded-concurrency runner (cap 3, matches PhotoSyncer) over a shared iterator. Per-project error toasts are rate-limited so a sustained R2 outage doesn't spam the user. Idempotent: every download checks `FileManager.fileExists` first, so a fully-populated device is a no-op. New iOS `APIClient` methods: `getPhotoImageURL`, `getPhotoThumbURL`, `getPlanImageURL`, `downloadBytesFromPresignedURL`. `ProjectStore` gains `planImageURL(for:in:)` (sibling of `imageURL(for:in:)` for photos). `SitePhotoApp` wires the new service into the launch sweep (after auth / appConfig / manifest pull / photo upload) and into the sign-in change handler. `SettingsSheet` "Sync now" also triggers backfill; sign-out calls `backfillService.reset()`. Storage-status footer text was misleading — previously read "Local storage only" on simulator + any signed-in install without iCloud. Now branches into three states: iCloud + backend (best), backend-only (signed in, no iCloud — backfills work, message says so), local-only (not signed in). Same branching applied to the SettingsSheet Storage section. Backfill progress chip in the footer surfaces `N/M (K failed)` while the launch sweep runs. iOS-only PR. No server / web / shared / supabase change.
