* **Summary:** Targeted speedups for the folder export. User saw 85/231 in 4m44s on the #5.106.1 build = 3.3s wall-time per photo with 4-way concurrency = ~13s per individual R2 fetch, which is wildly slow. Three changes: **(1) Skip deflate compression** — `archiver("zip", { store: true })` instead of `{ zlib: { level: 1 } }`. JPEGs + HEICs are already entropy-encoded; deflate adds 0% size reduction and burns CPU. Store mode makes the worker purely network-bound, which is what we want when network is the limiter. **(2) Bump fetch concurrency** from 4 to 12. If R2 latency is the bottleneck (likely Render → Cloudflare network), more in-flight requests help linearly until R2 starts throttling. **(3) Diagnostic logging** — per-photo timing surfaces in Render logs as `slow R2 read` warns when a single fetch exceeds 2 seconds. Per-bucket summary log line at the end shows `{ wallMs, avgFetchMs, concurrency }` so we can see whether the bottleneck is network (high avgFetchMs) or our code (low avgFetchMs but high wallMs implies queueing). No iOS change. No schema / migration change. No `manifestSchemaVersion` bump.
