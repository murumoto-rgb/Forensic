* **Summary:** Tail-end fix after #5.74.3 — Chromium now finds the binary AND the renderer loads real thumbnails, but the job fails mid-render with `Protocol error (Runtime.callFunctionOn): Target closed`. That's Puppeteer's standard "the Chrome page died" surface. Two stability fixes on the worker: (1) drop the `--single-process` + `--no-zygote` Chromium launch flags from `pdfWorker.ts`. Those were added in #5.62.1 for memory savings on Render free tier, but `--single-process` is a known cause of crashes during `page.pdf()` on large HTMLs — Chrome's PDF printer assumes multi-process isolation. Multi-process Chrome's RSS overhead is offset by the much higher stability under load. (2) New `recycleBrowser()` watchdog that tears down + relaunches the Chrome process every `BROWSER_RECYCLE_EVERY = 4` chunks. The relaunch costs ~1 s (negligible against a multi-minute export) but keeps RSS bounded across 30+ chunk exports — Chrome accumulates memory across navigations even when pages are properly closed. Plus: `PAGES_PER_CHUNK` drops from 25 to 10, giving each chunk a smaller HTML for Chrome to digest. For a 525-photo export at perPage=6 that means ~9 chunks of ~60 photos each instead of ~4 chunks of ~150 photos — more relaunches but each chunk fits comfortably in Render free-tier's memory budget. Server only — no schema change, no shared change, no iOS change, no web UI change. No `manifestSchemaVersion` bump.
