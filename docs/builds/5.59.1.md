* **Summary:** Foundation for the Collaboration-safety milestone (#6 + #10 bundled) — the project edit-lock model that the original plan called for in Phase 2 but was never built. (Confirmed during this session: "Unlock pins" on web is just a local accidental-drag guard, unrelated; no lock model existed.) New migration `0006_project_locks.sql`: one `project_locks` row per project (project_id PK), holder user_id + email, client ('web'|'ios'), acquired_at / last_heartbeat / expires_at. RLS lets any signed-in user SELECT (so a viewer's "currently editing" banner can name the holder); all writes go through the server secret key. New shared types in `api.ts`: `LockClient`, `ProjectLock`, `AcquireLockRequest`, `LockResponse`, `GetLockResponse`. New server route `server/src/routes/locks.ts` with five endpoints: `GET /v1/projects/:id/lock` (current lock or null — null when free OR row expired), `POST .../lock` (acquire — free/expired/mine succeeds, live-and-someone-else's → 409 with holder in details), `POST .../lock/heartbeat` (bump expiry; 409 `lock_lost` if not holder), `DELETE .../lock` (release, holder-only, idempotent), `POST .../lock/force` (force-release, any signed-in user for now since no admin role yet, logged as warn). Lock TTL is 10 min per heartbeat; expiry enforced in app logic (`expires_at < now()` treated as free) so no background reaper is needed. This PR is data model + endpoints only — no client wiring; web edit-lock UI lands in #5.60.1, emails in #5.61.1. Server + shared + migration. No iOS / web client change. No `manifestSchemaVersion` bump (locks are out-of-band, not in the manifest). Operator step before merge: run `0006_project_locks.sql` in Supabase SQL editor.
