* **Summary:** Bug fix on top of #5.74.1 — the PDF export rendered successfully on Render after the Chromium fix, but every photo tile showed "pending sync" placeholder instead of the actual thumbnail. Root cause: the renderer was assuming R2 object keys are deterministic (`${projectId}/${photoId}/thumb`), but iOS only uploads `kind="photo"` rows — there's no separate `thumb` row in the `files` table. The existing `routes/photos.ts` endpoint handles this correctly via a `files`-table lookup with thumb→photo fallback, but the PDF renderer didn't mimic that — every "thumb" key lookup missed in R2, every `fetchImage()` returned null, and every tile rendered the placeholder. New `resolveFileObjectKeysByPhotoId(projectId, ids, kindPreference, log)` helper in `htmlReport.ts` queries the `files` table for each id and picks the highest-priority kind that exists (matches `routes/photos.ts` logic exactly): `['thumb', 'photo']` for photos, `['plan']` for plans. PostgREST URL-length-cap-aware: sub-batches the IN clause at 100 ids per query, same way `routes/files.ts` does. Refactor: contact-sheet renderers (`renderUngroupedContactSheets`, `renderBucketedContactSheets`, `contactSheetPage`) and plan-page renderer (`renderPlanPages`) now take `Map<photoId, ImageBlob | null>` / `Map<planId, ImageBlob | null>` directly instead of `Map<R2-key, ImageBlob | null>` + deterministic key helpers. Deletes `photoThumbKey` / `photoImageKey` / `planImageKey` — they were the source of the bug. Top-level `renderReportChunks` now: (1) resolves keys via files table, (2) fetches blobs in one parallel pass keyed by R2 key, (3) builds the by-photoId/by-planId maps, (4) passes those down. New log line `pdf renderer — image resolution complete` surfaces per-job counts (photosResolved / plansResolved / blobsFetched) so future "all placeholders" regressions are diagnosable in one log search. Server only — no schema change, no shared change, no iOS change, no web UI change. No `manifestSchemaVersion` bump.
