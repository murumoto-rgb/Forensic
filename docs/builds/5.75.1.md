* **Summary:** PDF export now has a real progress indicator AND survives the user navigating away / refreshing — answering the three questions raised after the first successful Sarreon-2 export ("show progress", "does it stop if I leave", "where's the report if I leave"). **Progress:** new migration `0009_pdf_export_progress.sql` adds nullable `progress_done_chunks` + `progress_total_chunks` to `pdf_export_jobs`. The worker writes total chunk count at render start and bumps the done counter after each chunk (best-effort — a failed progress update never fails the render). New `PdfExportJob.progressDoneChunks` / `progressTotalChunks` fields (shared types); `rowToJob` maps them; the GET endpoint returns them via the existing `select("*")`. Web pill changes from a static "Rendering…" to "Rendering… N / M (X%)" driven by `progressLabel(job)`, with a pulsing dot. **Persistence:** the active `jobId` is now written to `localStorage` (key `forensic.pdfExport.activeJob.<projectId>`, scoped per project) when a render starts, and cleared on done / failed / error / reset. On mount, `ExportPdfControl` reads that key and — if present — resumes polling the same job, so a refresh or navigate-back reconnects to the in-flight render and surfaces the download when ready. **Answers to the three questions, documented in code comments:** (1) progress is now visible per-chunk; (2) the render does NOT stop when you leave — it runs entirely server-side in the worker, independent of any browser tab; (3) the finished PDF lands in R2 at `exports/pdf/<jobId>.pdf` and is reachable via `GET /v1/exports/:jobId` (which presigns a fresh 5-min download URL on demand) — the localStorage handle is what lets the UI find it again after a navigation. Server + shared + web. **Operator step before merge:** run `0009_pdf_export_progress.sql` in the Supabase SQL editor. No `manifestSchemaVersion` bump.
