* **Summary:** Client-side folder export — fixes the Render free-tier ceiling that's been killing 300-photo exports across #5.97 → #5.109. New architecture: server returns a manifest of presigned R2 URLs; **the browser downloads photos directly from R2 and builds the ZIP locally via JSZip**, taking the streaming + memory work off Render entirely. New server endpoint `GET /v1/projects/:id/folder-export-manifest` does one project-table read + two `files`-table reads + parallel R2 presigning — costs ~200ms server-side, no streaming, no memory pressure. Returns `{ projectName, buckets, photos: [{ presignedUrl, filename, ... }], plans: [...], totalSizeBytes }`. New shared types `FolderExportManifest*` capture the response. New `web/src/components/FolderExportClient.tsx` component: clicks "Download folder bundle…" → fetches manifest → downloads photos with 6-way concurrency directly from R2 → JSZip with `STORE` mode (no compression — photos don't compress) and `streamFiles: true` → triggers a Blob download via the standard `<a download>` mechanism. Live progress bar `X / Y · NN%` during download phase, separate progress during zip-build phase. ExportTab's "Folder by Bucket" card now defaults to the client-side flow; a collapsible `<details>` section underneath exposes the legacy server-side path for users who need the bundle to survive closing the tab. JSZip added to web/package.json (^3.10.1). Server-side worker (#5.108.1 + #5.109.1) stays in place — useful for the rare case where the user wants the export to run unattended. No iOS change. No schema / migration change. **For 300-photo exports the wall time should now be limited only by the user's home internet downstream and laptop CPU/RAM — typically 2-5 minutes on a normal connection.**
