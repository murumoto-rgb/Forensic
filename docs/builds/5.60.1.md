* **Summary:** Web edit-lock UI on top of the #5.59.1 foundation — second half of the Collaboration-safety milestone (#6 + #10 bundled; emails follow in #5.61.1). New `useProjectLock(projectId)` hook in `web/src/lib/useProjectLock.ts` owns the lifecycle: discriminated `LockStatus` (`loading` | `free` | `holding` | `read_only` | `lock_lost` | `error`), 30s viewer poll (paused while we're the holder so we don't fight the server's view of who has it), 90s heartbeat while holding (server TTL is 10 min so a few missed beats don't drop it), `beforeunload` release via `fetch(..., {method: "DELETE", keepalive: true})` (chosen over `sendBeacon` because beacons can't issue DELETE), and a hard release on unmount. 409 on acquire pulls `details.lock` into a read-only banner; 409 on heartbeat flips status to `lock_lost` so the user sees a re-acquire prompt. New `LockBanner` component renders one of five shapes per status (loading placeholder, Edit button when free, green "you're editing" with Release when holding, amber "currently editing: alice@…" with Force release confirmation when read-only, red "lock was lost" with Re-acquire/Dismiss). Wired into both edit surfaces: `ProjectPlanPage` (pin drag + distress add/edit + AI re-tag via preview panel) and `ProjectDetailPage` (batch "Re-tag all with AI"). When the lock isn't held the page hides the "Unlock pins" / "Add distress" toggles entirely, drops `onPhotoUpdated` on the preview panel (which already gates accept/reject suggestion + Re-tag affordances on that callback), and hides `BatchRetagControl`. Local edit-mode toggles auto-clear if the lock evaporates mid-edit. Five new API client methods on `web/src/lib/api.ts`: `getProjectLock`, `acquireProjectLock`, `heartbeatProjectLock`, `releaseProjectLock`, `forceReleaseProjectLock`. Web only — no server, iOS, or shared change. No `manifestSchemaVersion` bump (locks are out-of-band).
