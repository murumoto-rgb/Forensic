* **Summary:** Cloud-first **Phase 1, PR 1.2** — the server now consumes the 3-way merge from #5.116.1 on `PUT /v1/projects/:id`. When the client sends `baseManifest`, the server fetches the current stored manifest, runs `mergeManifest(baseManifest, current, project)`, and writes the merged result via a **compare-and-swap update with bounded retry** so two concurrent writers (web + iOS, or two web tabs) both land — no lost write, no 409 surfaced to the user. The merged manifest is returned in the response so clients can adopt it. When `baseManifest` is absent the **legacy optimistic-concurrency path runs unchanged** (back-compat) — old web/iOS binaries keep working exactly as before. Implementation details: CAS guard is `.update(...).eq("id",id).eq("revision",expectedServerRev).select("id")` — `rowCount === 1` confirms; `0` means another writer raced us, so we re-fetch and re-merge (idempotence guarantees convergence). Retry budget is 3 attempts (1 retry covers the common case; 3 is a safe ceiling for concurrent storms); on exhaustion the server returns `409 merge_cas_exhausted` so the client retries on its next save tick. `MergeReport` is logged at `info` whenever both-changed scalars forced a winner — observable for audit, never blocks the write. Create-path (no existing row) falls through to the legacy upsert. **This is the PR that must deploy before any client sends `baseManifest`**; PR 1.3 (web) and PR 1.4 (iOS) land after. No DB migration. No client surface change yet. No manifest-model change → parity untouched.
