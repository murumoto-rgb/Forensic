* **Summary:** **Performance PR 3 of the iOS review (Wave 2): concurrent photo uploads.** `PhotoSyncer.syncProject` uploaded strictly one object at a time, and each photo is three sequential network round-trips (getUploadUrl → R2 PUT → commitUpload) — so a fresh-install backfill of hundreds of photos spent nearly all its wall-clock waiting on latency. The per-photo loop is now a **bounded task-group window: 4 photos in flight at once** (each photo's full-res → thumb pair stays sequential within its unit so a thumb never lands before its photo). State stays MainActor-serialized — `PhotoSyncer` is `@MainActor`, child tasks hop onto the actor between network awaits — and the existing `inFlight` set still dedupes overlapping sweeps. Width 4 hides round-trip latency without saturating a field uplink or hammering the server. **Also moved the per-photo `Data(contentsOf:)` read + SHA-256 off the MainActor** into a detached task — with four uploads interleaving, multi-MB reads + hashes on the main thread would have dropped frames during a backfill (`sha256Hex` becomes `nonisolated`; statics on a `@MainActor` class are actor-isolated by default and it's now called from the detached context). The R2 pre-check (bulk "what already exists" query from #5.x) runs unchanged before the window starts. Plans stay serial (N ≤ 5 per project). Error handling per upload is unchanged (silent skip + console log; tracker untouched on failure so the next sweep retries). No DB / shared / server / web change; the server's presigned-URL endpoints already handle concurrent callers (web uploads with 3-way concurrency since #5.90.1).
