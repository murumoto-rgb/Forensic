* **Summary:** Fix the slow folder export shipped in #5.97.1 / #5.105.1. Three issues addressed at once: **(1) Parallel R2 fetches** — the worker previously fetched every photo serially (300 photos at ~200ms each = 60+ sec just in network latency, plus more for bigger HEIC blobs). New `parallelFetch` helper runs four downloads concurrently while keeping the `archive.append` calls strictly serial in sequence-number order (parallel I/O, serial CPU + stream backpressure). Should bring a 300-photo project from 15min to ~2-3min. **(2) Progress tracking** — new migration `0012_project_exports_progress.sql` adds nullable `progress_done` + `progress_total` columns to `project_exports`. A `ProgressWriter` class in the worker writes `progress_done` to the row every 5 items completed (throttled to avoid hammering Postgres). The Exports page renders a live progress bar (X / Y · NN%) for `status="running"` rows, plus a "Running 2m 14s" elapsed timer that ticks every second between the existing 3-second list polls. **(3) Properly await archive.finalize()** — the previous code swallowed finalize errors with `.catch(...)` and only awaited the upload, which left the upload hanging if finalize threw before piping the end-of-stream signal to PassThrough. Now we `await archive.finalize(); await uploadPromise;` so errors surface and the multipart upload only closes after every entry has been flushed. Shared `ProjectExport` interface gains `progressDone` + `progressTotal` (both nullable). Server route's `ExportRow` interface + `rowToProjectExport` mapper updated. Migration 0012 must be applied to staging before progress UI populates. No iOS change. No manifest change. No `manifestSchemaVersion` bump.
