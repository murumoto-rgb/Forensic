* **Summary:** **Phase 2** — fixes the "back-button self-lock" bug. Today when a web user takes the edit lock and back-navs away, the unmount cleanup's DELETE often doesn't land; the 10-minute lock row survives; on return the user appears to themselves as locked out by their own stale lock. **Root cause** (confirmed at `useProjectLock.ts:81-85`): the GET handler deliberately renders any live lock as `read_only` — even the caller's own — because the server couldn't tell which of the user's tabs was asking. **Fix**: each browser tab gets a stable UUID stored in `sessionStorage` (semantics: persists across same-tab back/forward, unique per tab) and sends it on acquire, heartbeat, GET, and release. Server records it on the lock row in a new nullable `project_locks.client_session` column (migration `0013_project_locks_session.sql`). The GET response gains a `heldByYou: "session" | "user" | null` discriminator — the server computes it from the caller's `user_id` + the session token sent in `?clientSession=`. The web hook maps it: `"session"` → resume `holding` (the back-nav return — **the bug fix**), `"user"` → new `holding_elsewhere` status ("You're editing this in another tab — Resume here"; clicking acquire re-acquires for the same user), `null` → `read_only` / `free` unchanged. `LockBanner` gets the new branch. **Bonus reliability**: release on `pagehide` (more reliable than `beforeunload`; works on mobile Safari) via authenticated `keepalive` fetch to a **new** beacon-friendly `POST /v1/projects/:id/lock/release` endpoint that takes the session token in the JSON body (sendBeacon can't set the Authorization header so we use a keepalive fetch with the JWT cached in a ref via `onAuthStateChange`). DELETE `/lock` and the new POST `/lock/release` both scope the delete to the caller's session when one is sent, so closing tab A doesn't free tab B's lock. **iOS**: unchanged — sends no session token; rows carry `client_session = null` and behave exactly as today (no per-tab granularity needed; iOS is one-process-one-user). **Parity**: `ProjectLock` is a server wire type, not a manifest model — no `MANIFEST_SCHEMA_VERSION` bump, no `ios-models.json` change, parity contract test unaffected. New endpoints + DB column are additive; old clients (no token sent, no `heldByYou` in response) keep working unchanged.
