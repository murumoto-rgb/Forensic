* **Date:** 2026-06-08

* **Merge SHA:** 4f893b1
* **Summary:** Cache photo thumbnail URLs across filter changes so toggling a tag or bucket no longer re-downloads every thumbnail. **Before**: `PhotoList`'s useEffect keyed on the joined list of filtered photo IDs; every filter toggle changed that key → effect refired → `setUrlsState({ kind: "loading" })` blanked the grid → `getPhotoUrlsBatch` hit the server with the new ID set → all thumbnails reloaded from R2 even though most were already in browser cache (and the same R2 blobs as before). **After**: URLs live in a `useRef<{ urls: Map<photoId, string>; attempted: Set<photoId> }>` that persists across renders. The effect computes `missing = photos.filter(p => !attempted.has(p.id))` and only calls the server for actually new IDs. Filter-only changes (same photos, different visibility) short-circuit with `setUrlsState({ kind: "ready", urls: cache })` and never trigger a network request. The `attempted` set records IDs we've already requested (successful OR 404'd) so missing-on-server photos don't keep retriggering on every filter toggle; on transient network errors we roll the flag back so a future render can retry. Cache is reset when `projectId` changes (URLs are project-scoped). First-mount UX preserved: `loading` state shows only when the cache is empty; on subsequent fetches (e.g. user uploaded new photos) the existing thumbnails stay visible while the new IDs resolve in the background. No state shape change for downstream consumers — `PhotoListRow` still receives a flat `Record<string, string>` via a cheap `snapshotUrls` helper. No iOS / schema / API change.
