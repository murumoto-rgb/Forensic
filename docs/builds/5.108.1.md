* **Summary:** Folder export now streams photo bodies through the zip instead of buffering each photo into RAM. #5.107.1's concurrency-12 bump OOM'd Render free tier ("used over 512MB") because each in-flight photo held its full ~5-8MB body in memory: 12 × 8MB = ~100MB of buffers alone, plus archiver's pending entries + multipart upload's 5MB part + Node baseline. **(1) New `getObjectStream(key)` helper in `r2.ts`** returns the R2 GET response body as a Node `Readable` instead of resolving to a fully-loaded `Buffer`. Body bytes flow lazily as archiver consumes the stream — memory cost is per-socket overhead (~64KB) instead of full body. **(2) Worker rewritten to stream**: `parallelFetch` is now generic (`<T, U>`) and yields a stream per photo; the serial append loop attaches each stream to the next archive entry and `await`s an `entry` event before moving on. This guarantees the previous photo finishes flushing through PassThrough → upload before the next photo's stream is attached, so backpressure works and exactly-one body is "live" at any moment. **(3) Concurrency bumped to 8** — memory now bounded by sockets not body sizes, so we can be more aggressive. **(4) New `getObjectSize(key)` helper** does a HEAD after upload completes — the worker no longer accumulates per-photo byte counts (we stream); the final `size_bytes` column comes from a single HEAD on the uploaded zip. **(5) Diagnostic log key renamed** `avgFetchMs` → `avgHeaderMs` to reflect that streaming fetches resolve on response headers, not full body. Total memory profile per run: ~50MB peak (Node baseline + Fastify + Sentry) + ~5MB (upload part buffer) + ~512KB (8 R2 sockets) + ~5MB (one body streaming through). Comfortably inside 512MB. No iOS change. No schema / migration change.
