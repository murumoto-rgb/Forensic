* **Summary:** **New GitHub Actions cron to keep the Supabase project from pausing.** Supabase free-tier projects pause after ~7 days of inactivity (no DB queries / API requests) and can only be resumed manually from the dashboard. The existing `keepalive.yml` pings the Render server's `/healthz` every 14 min to keep that *process* warm, but `/healthz` (`server/src/routes/healthz.ts`) returns a static object and never touches Postgres — so it does not count as Supabase activity and the database could still pause out from under a warm server. New `.github/workflows/supabase-keepalive.yml` runs daily at 07:00 UTC (plus `workflow_dispatch` for manual runs) and issues a minimal real query — `GET /rest/v1/app_config?select=key&limit=1` against the Supabase REST API — which executes a query against Postgres and resets the inactivity timer with ~7× margin under the pause window. Auth uses two repository secrets, `SUPABASE_URL` + `SUPABASE_SECRET_KEY` (the same values already on Render per `render.yaml` / `server/.env.local.example`); the workflow no-ops gracefully when they're unset, mirroring the Render keepalive's forked-repo-safe pattern. `-f` makes a paused project or a bad key/URL fail the job loudly — the intended "go resume it" signal, since a ping can't un-pause an already-paused project. The workflow header carries a security note: the secret key bypasses RLS but lives as an encrypted, log-masked Actions secret in a private repo (same exposure class as Render), with the lower-privilege anon-key alternative documented inline. **Parity check:** ops/infra only — no app code, no migration, no manifest model, no `manifestSchemaVersion` bump; parity contract unaffected.
