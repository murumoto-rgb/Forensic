* **Summary:** Defensive fix + diagnostics for the SIGTERM the user saw at 125/231 photos on #5.108.1. No OOM log this time — Render's container watchdog killed the process for a different reason (port-scan starvation, suggesting CPU/memory pressure that didn't quite trigger strict OOM but was high enough for Render's eviction). **(1) Concurrency 8 → 3** to give Render's free-tier scheduler more headroom. With streaming bodies the memory cost is per-socket, so 3 in-flight is ~192KB of socket buffers + 1 streaming body + Node baseline. **(2) Memory snapshot every 10 photos** — RSS, heapUsed, heapTotal, external. Logged at `info` level under `"folder export — memory snapshot"` so we can watch memory growth in Render's log stream while a run is in progress. Critical for diagnosing whether the next failure is leaks, GC pressure, or just hitting the wall. Honest sidebar: Render free tier (512MB shared CPU, auto-spin-down) isn't designed for multi-minute streaming workloads. Render Starter ($7/mo, dedicated CPU, no spin-down) is the lowest tier that should reliably complete 300+ photo exports. This PR helps but doesn't fundamentally change that constraint. No schema / migration / iOS change.
