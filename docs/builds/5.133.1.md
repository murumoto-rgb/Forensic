* **Summary:** **Fixes a misleading batch-tagging error message.** `BatchTagSummarySheet.friendlyMessage` previously rewrote *every* HTTP-status failure as "Anthropic API error (NNN) — likely rate-limit or content filter; retry usually works." That's actively wrong for a 503: when the team server has no `ANTHROPIC_API_KEY`, `POST /v1/ai/tag-photo` returns `503 service_unavailable` instantly for every photo, and "retry usually works" is false — retrying fails identically (exactly the 0-tagged / 229-failed result the user hit). Now `friendlyMessage` branches on the parsed HTTP status: **429** → rate-limit (retry with backoff; suggests lowering Parallel AI requests); **529** → Anthropic overloaded (retry works); **503** → surfaces the **server's own message** ("AI tagging is not configured…") instead of the canned rate-limit text, since a 503 from our server is a configuration problem retrying won't fix; **401/403** → credentials rejected, check the server key; **other** → pass through the raw server message rather than inventing a cause. New `httpStatus` computed property parses the status from `(NNN)` or a standalone 3-digit run. View-layer only — no behavior change to the tagging dispatch itself. **Root cause of the user's failure is separate and operational**: `ANTHROPIC_API_KEY` is unset on the Render server (the team-server AI path's shared key); must be set in Render → Environment. This build only makes the error message tell the truth about that. No DB / shared / server / web touched; parity contract green.
